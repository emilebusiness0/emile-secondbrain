When building something that will live in an external web app (Google Sheets + Apps Script, a config file, etc.), prefer writing the deliverable to a local file and handing it to the user to import/paste themselves, rather than driving a live browser automation session to click through the UI.

**Why:** confirmed directly by Emile (2026-07-30) — on a previous device, this was the standard workflow and he noted it was faster, used far fewer tokens, and produced a cleaner result. Live browser automation for this kind of task is slow, token-heavy, and fragile — hit real problems doing it live: hung Apps Script "Run" executions, an OAuth consent popup requiring manual clicks, and a nasty Google Sheets API bug (`getLastRow()` false-positive from checkbox/validation formatting on empty rows, causing `appendRow()` to silently write data hundreds of rows below the visible area).

Second incident (2026-07-31): while driving the Apps Script code editor live to *inspect* it (not even to build), keyboard shortcuts I sent didn't behave like shortcuts — `Ctrl+F` and `Page_Down` were typed as literal text directly into the live script instead of opening find/scrolling. Had to undo/backspace it out under time pressure, and a safety classifier then blocked further delete/backspace keystrokes in that tab, stalling recovery. Confirms the code editor's shortcut surface is unreliable for automation, not just risky for building.

**How to apply:** When the deliverable is something like an Apps Script project, a spreadsheet structure, or similar — write the complete file(s) locally (e.g. a `Code.gs` script), give it to the user, and brief them on the single manual step (e.g. "paste this into Extensions > Apps Script, save, run setup()"). Only fall back to live browser-driving when the task genuinely requires interacting with existing live state that can't be reconstructed from a file. This applies to *inspecting* the Apps Script editor too, not just writing to it — prefer read-only extraction (see [[feedback/browser-verification-token-cost]]) over clicking/typing inside that editor even just to look.

Third incident (2026-08-01): after the same live-browser Sheets automation failed again (Name Box navigation and arrow-key navigation both silently no-op'd, coordinate clicks landed on wrong cells due to a screenshot/real-viewport scale mismatch, one stray click accidentally toggled a checkbox), I pivoted to giving Emile step-by-step manual instructions (find this menu, paste this one function, run it, then edit these two lines elsewhere in the file) instead of just handing him one complete script to paste wholesale. Emile pushed back hard: multi-step piecemeal instructions are more work and more error-prone for him than one paste. **Default to the single-paste full-file answer, not incremental edit instructions, whenever the deliverable is a script/config file he can just replace wholesale** — don't ask him to hunt for a specific line/menu when the whole file can be regenerated and handed over instead. Same principle as the core lesson above, but explicitly extended to *editing* an existing script, not just building a new one.

Exception confirmed by Emile (2026-08-15): for reviewing/restructuring the Google Ads campaign, he wants a collaborative live-browser session — he logs in and clicks himself, I read the page (read_page/get_page_text) to see current state and advise, rather than building a file for him to import. This fits the existing rule (I still don't drive clicks/credentials), it's just that Google Ads campaign review specifically works better live than as a generated deliverable, unlike Sheets/Apps Script.

Fourth incident, explicitly extended to per-client quote docs (2026-08-18): asked to edit the Duo Vert soumission template Google Doc for a new client (Lisette). Drive `create_file`/`copy_file` both errored repeatedly (connector-side outage), so fell back to live-editing the doc in the browser pane after Emile signed in there — hit the exact same shortcut-typed-as-literal-text failure as the second incident (`Cmd+Shift+H` for Find & Replace typed "h" then "z" into the title instead of opening the dialog), and this time Backspace/Delete *also* silently no-op'd repeatedly even with the stray text selected, leaving "hzDUO VERT" stuck in the live doc that Emile had to fix by hand. Emile interrupted to push back: quote generation should take seconds, and Google Docs shouldn't be the default tool for it at all. **Decision: stop using Google Docs (create_file, copy_file, or live browser editing) as the default path for per-client quotes.** New default going forward: generate the quote as a **PDF locally on his Mac** (per [[duo-vert/soumission-template]] for the field/pricing structure) and hand it to him as a file to send directly — no Docs/Drive/browser step in the normal flow. Docs is now a fallback only, not the default, same demotion this file already gave Sheets/Apps Script.

Fifth incident (2026-08-20): tried typing new lead rows directly into the live Pré-soumission sheet via cell-click + type + Tab-across-the-row — a *data entry* task, not building structure, so it seemed like a reasonable exception. Typed a full row (lead number, date, name via Tab-separated keystrokes) and it silently no-op'd completely — cell A6 stayed empty, no error. Escaped cleanly before any stray text could land, confirmed no corruption, and abandoned live typing entirely. **Extends the rule to data entry, not just structure-building** — even adding a few rows to an already-built sheet isn't safe to type live.

**Working alternative found the same day — CSV + "Append to current sheet" import:** read the target sheet's exact column headers via screenshot/zoom (read-only, no typing), built a headerless CSV matching that exact column order, handed it to Emile as a file, and had him do **File → Import → Upload → Import location: "Append to current sheet"**. This drops new rows in cleanly at the bottom of the currently-active tab without touching existing data validation/checkboxes on other rows, and needs zero live typing from either of us. This is now the **default method for adding rows to an existing live Sheet** (as opposed to full-file replacement, which is the default for building/editing a whole script or structure) — see [[duo-vert/sheets-tracking]] for the current Pré-soumission column layout this was built against.
